# 让业务系统从“点点点”变成 Agent 能力：我做了 Code2Skill

很多公司其实并不缺少业务能力。

客户查询、订单处理、售后跟进、内部申请、数据统计……这些功能早已存在于公司的前端页面、后端接口和业务代码中。

但它们大多是为传统软件交互设计的：

> 用户打开系统 → 找到页面 → 查询或填写信息 → 点击按钮 → 完成操作

即使公司接入了大模型，Agent 往往也只能告诉用户“应该去哪个系统、哪个页面操作”，无法真正帮助用户完成这件事。

我一直在想：

> 既然现有代码里已经包含了业务接口、请求参数、数据结构和操作流程，能不能用一种相对简单的方法，把这些已经存在的能力提取出来，转换成 Agent 能够理解和调用的 Skill 与 MCP？

这就是我开发 [Code2Skill](https://github.com/leechen298/Code2Skill) 的原因。

目前项目已经发布正式版本：[v1.0.1](https://github.com/leechen298/Code2Skill/releases/tag/v1.0.1)。

## 我想解决的并不只是“少点几个页面”

把一个网页功能交给 Agent，最直观的价值是减少重复操作。

例如，过去用户需要进入系统、查找入口、填写表单并提交。转换之后，用户可以直接告诉 Agent 自己想完成什么，Agent 再逐步询问缺少的信息、调用业务能力，并把结果交还给用户。

但我认为更有价值的是后面两件事。

### 1. 让分散的信息更容易被 Agent 整合

很多业务信息分散在不同系统、菜单和页面里。人需要记住入口，并在多个页面之间来回切换。

如果客户、订单、服务记录和其他业务数据都能以 Tool 的形式提供给 Agent，那么 Agent 就有机会在权限允许的范围内：

- 汇总原本分散的信息；
- 发现数据之间的关联；
- 根据当前问题选择需要调用的能力；
- 帮助用户更快地理解情况和作出判断。

这不只是把网页换成聊天窗口，而是改变业务能力被使用的方式。

### 2. 让原本独立的功能可以临时组合

传统网页通常按照固定菜单和固定流程设计。

如果要把多个系统能力组合起来，往往需要重新设计页面、开发接口编排、安排测试并上线。对于低频需求，这个成本可能高到根本不会有人去做。

Skill 和 MCP 更像可以组合的能力单元。

当多个查询、计算和操作能力都可以被 Agent 调用时，Agent 可以根据用户当前的目标临时组合它们。过去实现起来繁琐，甚至没有被提前设计过的功能，可能通过几次 Tool 调用就能完成。

## 为什么从现有代码生成

让 Agent 使用企业能力，最常见的方法是重新整理接口文档，再手工编写 MCP Tool 和 Skill。

这种方式当然可行，但企业真实项目里经常存在几个问题：

- 文档不一定与当前代码同步；
- 一个业务流程可能分散在页面、组件和公共请求模块中；
- 同名字段在查询和提交时可能代表不同含义；
- 时间、附件、枚举和格式转换可能只写在前端代码里；
- 业务功能很多，完全依赖人工整理成本很高。

另一方面，能够正常运行的前端代码，本身已经是一份很有价值的“可执行说明”。

它至少能够告诉我们：

- 页面实际调用了哪些接口；
- 请求参数从哪里取得；
- 用户需要提供哪些信息；
- 接口之间如何传递数据；
- 提交前有哪些确定性的格式转换；
- 哪些步骤属于当前功能的主要流程。

Code2Skill 的思路，就是让编程 Agent 从用户授权的源码中理解这些信息，再生成可供其他 Agent 使用的能力包。

```text
现有前端或全栈代码
        ↓
    Code2Skill
        ↓
Function + MCP Tools + Skills + Tests
        ↓
Agent 获取信息并帮助用户完成目标
```

## Function、MCP 和 Skill 分别负责什么

Code2Skill 不会把所有内容都塞进一份提示词。

### Function：稳定地调用业务接口

Function 负责已经能够从源码确定的事情，例如：

- 请求地址和方法；
- 参数映射；
- 时间和格式转换；
- 上下游数据交接；
- 保留后端实际返回的数据。

这类确定性逻辑如果每次都交给 Agent 临时推理，结果容易受到模型、上下文和提示方式影响。

### MCP：把能力提供给不同 Agent

Function 会被包装成符合 MCP 规范的 Tool。

只要运行环境支持 MCP Client，并完成相应注册，Agent 就可以发现和调用这些能力。Code2Skill 默认生成本地 stdio MCP，也可以根据项目需要使用 Streamable HTTP。

### Skill：告诉 Agent 如何帮助用户完成目标

Skill 不是一段必须从头执行到尾的死流程。

它更像给 Agent 的业务使用说明：

- 当前 Skill 可以帮助用户完成什么；
- 通常需要哪些信息；
- 哪些信息可以动态查询；
- 什么时候需要调用哪个 Tool；
- 缺少信息时如何继续询问用户；
- 遇到后端返回时如何根据实际结果继续。

是否调用 Tool、以什么顺序获取信息、怎样理解响应以及是否需要继续询问，仍由实际工作的 Agent 决定。

## 我在开发过程中走过的弯路

Code2Skill 早期版本追求尽可能完整地分析前后端代码、生成大量契约和验证材料。

结果是，一个真实功能的生成可能需要两三个小时，产物也会变得非常庞大。大量时间并没有花在生成文件，而是花在 Agent 反复阅读源码、修正规范、补充证据和证明各种边缘情况上。

后来我重新调整了方向：

- 以前端实际调用的后端接口为主要能力来源；
- 后端代码主要用于补充公开的请求和响应结构；
- 优先保证主要用户目标能够完成；
- 确定性的请求转换进入 Function；
- 普通业务判断更多交给调用 Agent 和真实后端；
- 默认只做离线技术验证，不主动请求真实业务接口；
- 生成结果保持精简，深入源码 Review 变成可选能力。

这次调整的核心并不是降低质量，而是把精力集中到真正影响可用性的地方。

## 实际生成效果

我使用同一份匿名、多目标客户端源码，分别生成了三份独立结果。

为了避免只凭“感觉不错”来判断，我采用了两套评分：

- **主流程完成度**：用户能否通过生成的 Skill、Function 和 MCP 完成主要工作；
- **业务语义精确度**：生成结果是否准确还原源码已经证明的字段来源、请求转换和调用关系。

结果如下：

| 生成模型/运行配置 | 生成耗时 | 主流程完成度 | 业务语义精确度 | 综合参考分 |
|---|---:|---:|---:|---:|
| GPT-5.6 Sol（Ultra 模式） | 47 分 45 秒 | 9.6 | 9.0 | **9.4** |
| Kimi K3（Max 推理档位） | 约 93 分钟 | 9.5 | 8.0 | **8.9** |
| GPT-5.6 Sol（High 推理档位） | 20 分 29 秒 | 9.0 | 7.5 | **8.4** |

综合参考分按照“主流程完成度 60% + 业务语义精确度 40%”计算。

这组数据不是模型排行榜，也不能证明生成结果已经通过生产环境验收。三份结果都只进行了源码复核、离线测试和本地 MCP 协议验证，没有调用真实业务写接口。

它能够说明的是：对于同一份真实形态的多目标源码，Code2Skill 已经可以相对稳定地生成主要流程基本可用的能力包。

完整的匿名评估口径、扣分规则和结果记录可以在项目的[评估报告](https://github.com/leechen298/Code2Skill/blob/main/docs/evaluation.md)中查看。

## 如何开始使用

Code2Skill 本身是一组 Agent Skills，可以使用通用的 `skills` CLI 安装。

以 Codex 为例，只安装日常生成需要的 Skill：

```bash
npx skills add leechen298/Code2Skill \
  --skill code2skill-generate \
  --agent codex \
  --global \
  --yes
```

安装完成后，在需要提取业务能力的代码仓库中告诉 Agent：

```text
使用 $code2skill-generate，把 <页面、目录或功能路径>
生成为可运行的 Function、MCP 和 Skills。

允许搜索的源码根目录：
- <前端目录>
- <后端目录或协议目录>

以前端实际调用的接口为主要能力来源，
不调用真实业务接口。
```

生成结果默认放在：

```text
generated/code2skill/<feature-id>/
├── SKILL.md 或 skills/*/SKILL.md
├── function-core/index.mjs
├── mcp-tool/index.mjs
├── tests/
├── package.json
└── MCP-SETUP.md
```

`MCP-SETUP.md` 会说明依赖安装、环境变量和 MCP 注册方式。

需要注意，安装 Skill、注册 MCP、连接真实身份和完成业务验证是不同的状态。Code2Skill 不会把“文件已经生成”描述成“生产环境已经可用”。

## 生成之后仍然需要人做什么

Code2Skill 的目标不是 100% 自动还原所有业务细节。

真实项目中仍然建议由熟悉业务的人完成以下工作：

- 检查主要目标是否完整；
- 确认关键请求与实际业务含义；
- 配置运行环境和身份认证；
- 在授权条件下验证真实接口；
- 根据实际使用反馈继续修改 Skill 或 Function。

项目还提供了两个可选的 Review Skill：

- `code2skill-review-flow`：检查用户能否通过主要流程完成目标；
- `code2skill-review-source`：进一步检查请求字段、转换和调用链是否符合源码。

它们用于帮助用户发现问题，不是为了重新建立一套沉重的审计流程。

## 我对 Agent 应用的一点判断

过去我们使用业务系统，主要是人去适应软件设计好的菜单和流程。

Agent 出现之后，软件能力的使用方式可能逐渐发生变化：

> 用户表达目标，Agent 根据当前情况选择、组合并调用已经存在的业务能力。

很多企业并不需要从零开始建设这些能力。它们已经存在于每天运行的系统、接口和代码中，只是还没有被整理成适合 Agent 使用的形式。

Code2Skill 想做的，就是尽可能降低这个转换过程的成本。

它目前仍处于第一个正式版本，还有很多真实技术栈和业务形态没有覆盖。但我更希望后续优化来自实际使用：哪些项目能顺利生成，哪些流程容易遗漏，哪些产物在真实 Agent 中不够稳定。
